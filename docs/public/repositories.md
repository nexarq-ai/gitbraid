# Repositories and reviewed changes

Create a repository in the configured Cloudflare Artifacts namespace, or connect an existing repository in that namespace. Gitflare confirms its Artifacts remote and current branch head. For an empty repository or one with untouched Gitflare setup files, an Owner can import a ZIP as its first source commit. This does not import an arbitrary GitHub/GitLab URL or Git history, and matching a namespace name alone is not proof of external ownership.

ZIP import is available only before established source exists. It checks the current branch head again before writing, preserves setup files omitted from the ZIP, and requires repository Manage permission. Archives are limited to 5 MiB compressed, 500 files, 10 MiB expanded, and 1 MiB per file. Common secret, Git metadata, dependency, and build/cache paths are skipped; unsafe paths and special files are rejected. Review skipped entries and the exact base before committing. Existing source must be updated through proposals or the Artifacts Git workflow.

Live verification imported a ZIP into an empty repository through MCP and confirmed that exact-request replay returned the same commit. The imported tree included nested source/test files, binary assets, and an executable script, while `dummy.env` and `node_modules` were omitted. A separate initialized repository passed the UI selection, review, commit, and proposal-navigation flow. After source was present, Gitflare correctly reported that ZIP import was no longer available. These results apply to those fixtures.

Browse a branch, tag, or commit before creating a Proposal. Gitflare resolves refs to a commit SHA; use that immutable revision as the task base. A Proposal is a mission-backed change record containing the intended outcome, acceptance criteria, one to eight uniquely named agent assignments (two by default), discussion, revisions, and execution evidence. The form shows the target default branch and current HEAD. Creating a Proposal saves a draft; starting it is a separate action that consumes Cloudflare and model resources. Up to three agents run concurrently, with additional tasks waiting for a slot. The workspace-wide **Proposals** view remains available; the repository's Proposals view keeps changes grouped with their codebase.

The proposal form is available from **Create proposal**, `#repository/<repository-id>/proposals/new`, or the workspace route `#proposals/new`. It reads the current default-branch HEAD before submission and includes it as `expectedBaseSha`. A mismatch returns 409 and preserves the draft; refresh the base and review the new commit before submitting again. Start rechecks HEAD and pins execution to the commit current when the run begins. Live MCP `gitflare_proposal_base` returned the same branch and HEAD as the repository API. A stale base returned `STALE_PROPOSAL_BASE`, and a stale skill edit returned `STALE_SKILL_BASE`.

The repository has focused **Code**, **Proposals**, **Agents**, and **Checks** views. Agents shows each task record, its assignment, run state, fork/branch, commit, changed files, and errors. Checks shows individual results and the combined candidate result with the SHA each one covers. Each task is designed to work in a separate fork and sandbox. Individual checks can pass while their combined candidate fails. File overlap is a signal for review, not proof of a semantic conflict.

The repository's **Skills** view discovers `SKILL.md` files beneath `.agents/skills/`, `.claude/skills/`, `skills/`, and `docs/skills/`. It resolves the selected branch, tag, or commit to an immutable SHA and previews instructions from that revision. Discovery is read-only: it does not install or execute a skill. The bounded scan reports truncation and skipped files so an incomplete result is visible.

The skill editor creates or updates `docs/skills/<lowercase-slug>/SKILL.md`. A create or update submits exact Markdown (up to 64 KiB, with `name` and `description` frontmatter) against an exact base commit from a principal with contribute and execute access. Gitflare queues one deterministic trusted-editor task, runs existing checks, and records a proposal; it makes no model call and does not write directly to the default branch. A live MCP-created skill and a UI-edited skill each passed individual and combined checks, were approved, and landed. The canonical file contents were verified.

The **Cloudflare** project view lets an Owner search and filter the connected account catalog, select multiple Workers, D1 databases, Durable Object namespaces, Container applications, and Workflows, and label each with its environment. The current development project map contains seven resources: two Workers, three Durable Object namespaces, one Workflow, and one Container, all labeled `development`. The UI save, API read (HTTP 200), and MCP `get` returned identical records. Only the dedicated Gitflare runner was associated from the three Container applications in the catalog. Container usage counters are unavailable. D1 migration has not been exercised live.

The Proposal's discussion is attached to the exact candidate SHA, base SHA, and execution epoch. Reviewers can comment or request changes; unresolved requests block approval and landing. Only the reviewer who raised a request can resolve it. Discussion is not an approval action and does not change source files.

Approve only the exact candidate and base SHAs shown in current evidence. Landing is separate and rechecks the approved candidate, passing checks, and canonical branch head before writing the tested commit. Landing does not deploy production. Cancelled or retried attempts retain distinct evidence; do not treat a queued state or agent summary as a passing result.

Preview uses a separate origin and an expiring capability tied to the candidate. A live preview opened successfully for a passing combined candidate and displayed that candidate's batch, concurrency, in-flight, and capacity values. This verifies one preview path; it does not establish compatibility for arbitrary applications or make the URL a public deployment.

The current execution policy is deliberately narrow: candidate edits are limited to `src/`, `docs/`, and `README.md`, while tests, test configuration, and dependency files remain protected. This is not a general Git host or arbitrary-language build service. A live three-agent proposal completed three concurrent model-backed runs, passed all individual checks and the combined check, and landed at the approved candidate SHA. Each run loaded the same landed skill manifest with zero warnings; all three outputs included a marker specified by that skill and absent from the task prompts. A separate two-agent fixture passed the combined check, opened in a separate-origin preview, and landed at its exact approved commit. Another proposal passed its individual checks but failed its combined check and remained unlanded. These are fixture results, not arbitrary-repository readiness or production deployment.
