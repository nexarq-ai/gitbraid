# Connect an AI client through MCP

Gitflare's MCP endpoint is `https://<your-worker-host>/mcp`. The Worker uses Cloudflare's official Agents SDK handler and routes tool operations through the same access checks as the UI. An MCP client receives the authority of the person who authorizes it; it does not receive a new Owner role.

![A remote MCP client completes OAuth authorization with the user, then calls bounded tools through the shared Gitflare authorization and API boundary](gitflare-diagram:mcp-connection)

## OAuth connection

The deployed OAuth Provider supports dynamic client registration, authorization-code PKCE with S256, a browser consent page, short-lived access tokens, refresh tokens, and account-role checks on each request. A live protocol check completed client registration, consent, PKCE exchange, MCP initialization, and session revocation; the revoked session then returned 401. The consent page shows the client's claimed name/domain, redirect host, workspace, and role. No actual Claude or Codex application connection has been verified, so client-specific setup may differ.

To connect an OAuth-enabled deployment:

1. Add a remote MCP server in your AI client using your Gitflare endpoint ending in `/mcp`.
2. Start the client's OAuth connection flow and review the browser consent page. Confirm the client identity and redirect destination carefully; a displayed client name may be self-reported.
3. Sign in to the intended Gitflare workspace and approve only the workspace access you expect.
4. In the client, discover Gitflare tools, list repositories, and read a file at a returned commit SHA. Confirm the response belongs to the intended workspace before authorizing writes.

For installations configured without OAuth storage, the server can also accept an account's personal bearer token. Use the client’s secure token store or environment-variable configuration; never paste the token into a prompt, repository file, or task assignment. The self-host installer is designed to create OAuth storage unless an existing namespace is supplied.

## Shared authority and limits

Current source and deployment expose 32 tools covering repository reads, initial ZIP import, model connections, Proposals, task history, documentation, access administration, review, cancellation, preview, and landing. Live discovery and baseline repository/documentation reads passed. Model registry and import-status APIs return HTTP 200. Live ZIP import and exact replay passed, with a separate UI import workflow also verified. Bounded text inference passed for Gateway Luna, Gateway `openai/gpt-4.1-mini` using compatible chat, and Workers AI Llama through Gateway `gitflare`. A custom Gateway model completed one live coding proposal with passing individual and combined checks and exact-candidate landing; approval and landing were owner-authorized agent actions, not independent human approval. A Workers AI Llama run completed a real tool loop and its candidate passed individual and combined checks, but the requested guide was too incomplete for approval and was not landed. This demonstrates a tool-capable checked candidate for that run, not successful delivery or general coding compatibility.

`gitflare_create_repository_skill` and `gitflare_update_repository_skill` queue exact-base proposals for `docs/skills/<lowercase-slug>/SKILL.md` (64 KiB maximum, required `name`/`description` frontmatter). They require repository contribute and execute permissions. A deterministic trusted editor applies the Markdown without a model call and runs repository checks. Exact candidate/base SHA checks and idempotency rules apply through MCP just as they do in the UI. Starting a mission consumes cloud and model resources. An authenticated client can approve or land only when the user authorized the action and the current role and state checks allow it.

`gitflare_model_connections` reads enabled workspace models and Gateway status. Owner-only `gitflare_manage_model_connection` adds, removes, or verifies a model. Gateway entries use a provider/model identifier and the OpenAI Responses or compatible Chat Completions transport; a documented Workers AI model is available through the configured Gateway binding. Keep provider credentials in AI Gateway `gitflare`. Proposals pin the selected enabled model per assignment, and execution does not silently substitute a different model. Verification is a bounded text inference and does not prove tool support. Text inference was verified for the three model configurations listed above. A custom Gateway model completed one live coding proposal through checks and exact-candidate landing; the approval and landing were owner-authorized agent actions, not independent human approval. A Workers AI Llama run completed a real tool loop and produced a candidate that passed both check levels, but its one-line change did not adequately answer the task, so review blocked approval and it was not landed. This demonstrates tool use and candidate checks for that run, not successful delivery or general coding compatibility.

`gitflare_repository_import_status` checks whether an Artifacts repository is empty or has only untouched setup files. Owner-only `gitflare_import_repository_archive` imports one base64 ZIP as the first code commit, with an exact expected HEAD and an idempotency key. It accepts up to 5 MiB compressed, 500 files, 10 MiB expanded, and 1 MiB per file. It preserves omitted platform setup files, skips common secret/Git/dependency/build paths, rejects unsafe paths and special files, and does not import Git history or overwrite established source. Replay the same request to reconcile an uncertain result. A live MCP import and replay returned the same commit; the resulting tree confirmed the intended files and omissions. A separate UI import passed ZIP selection, review, commit, and transition to proposal creation.

`gitflare_cloudflare_project` manages per-repository Cloudflare resources. Its `map` action accepts up to 100 `{type, id, name, environment}` records. Resource types are `worker`, `d1`, `durable_object`, `container`, and `workflow`. Use IDs from the connected account catalog; only an Owner can change the map. `usage` returns per-resource Worker and D1 metrics; unsupported resource counters are returned as unavailable, not estimated. D1 migration planning requires a current commit and SQL migration path, and requires an explicit `databaseId` when multiple D1 resources are mapped. Review the SQL and checksum before the destructive execute action. An unknown outcome must be inspected, not automatically retried. Worker Builds triggers and Durable Object migrations are unavailable.

The current development project map contains seven resources: two Workers, three Durable Object namespaces, one Workflow, and one Container, all labeled `development`. The UI save, resource API read (HTTP 200), and MCP `get` returned identical records. Only the dedicated Gitflare runner was associated from the three Container applications in the catalog. Container usage counters are unavailable. D1 migration was not exercised.

External MCP clients and runtime task agents have different credentials. A remote Claude or Codex client acts as the human principal; a product coding task receives independently scoped access to its own fork. Never pass an Owner token, OAuth client token, personal MCP bearer, deployment secret, or setup token into a task sandbox.

No actual Claude/Codex application OAuth session has been verified. A live three-agent fixture has completed individual and combined checks and landed at the exact approved commit; a separate two-agent fixture also passed, landed, and opened in a separate-origin preview. This does not establish client-specific compatibility or arbitrary repository readiness.
